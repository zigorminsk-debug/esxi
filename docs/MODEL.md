# Расчётный стенд: формулы, границы и проверка

Это **дискретная детерминированная модель**, а не эмулятор VMkernel. Она не подключается к ESXi, не выполняет команды, не измеряет реальные счётчики и не разворачивает ВМ. Цель — выявить заведомо нехватку ресурсов, показать конкуренцию ролей и сформировать проверяемый план настройки.

## Входные диапазоны

| Параметр | Диапазон | Единица |
|---|---:|---|
| CPU sockets | 1–2 | шт. |
| Cores per socket | 10–50 | физических ядер |
| CPU frequency | 2–6 | GHz, шаг 0,1 |
| RAM | 12–1024 | GiB |
| SSD count | 1–5 | отдельных устройств |
| Each SSD | 512–2048 | GB |
| HDD count | 1–5 | отдельных устройств |
| Each HDD | 1000–32000 | GB |
| LAN ports | 1–5 | физических NIC |
| Port speed | 1–25 | Gbit/s |
| SSD IOPS per device | 1000–300000 | модельное допущение |
| HDD IOPS per device | 50–500 | модельное допущение |

Пользователь может включать/отключать роли, добавлять до 40 рабочих ВМ, менять имя, CPU, RAM, диски и активных пользователей. Для Bitrix это активные посетители. «ТП» трактуется как техподдержка; название можно изменить. VCSA Tiny и виртуальный firewall включаются отдельно.

## Вычисление нагрузки

Окно моделирования — 60 условных минут. Один шаг в секунду меняет время на минуту; ползунок позволяет исследовать любую точку. Профили: рабочий день, пик, backup, ночь. Нет случайности: одинаковый ввод и время дают одинаковый результат.

Для каждой роли заданы стартовые CPU/RAM/диски и коэффициенты нагрузки на пользователя. Это **авторские учебные коэффициенты**, не нормативы Broadcom, Microsoft, 1С или Bitrix.

- Физические ядра: `sockets × coresPerSocket`. Hyper-threading не удваивает ёмкость.
- Условная CPU-ёмкость: `physicalCores × GHz`.
- CPU demand ВМ: `max(0.1, vCPU × 0.2 + users × roleCpuFactor × scenarioFactor + backupOverhead)`.
- Для SQL/1С/RDP пиковый профиль дополнительно умножает пользовательскую часть на 1,2.
- Активная RAM: `min(configuredRAM × 1.12, configuredRAM × 0.35 + users × roleRamFactor × scenarioFactor + backupOverhead)`.
- Резерв гипервизора: `max(4 GiB, RAM × 0.08)` — приближение, не точный overhead VMware.
- IOPS: пользовательская нагрузка роли + базовый фон. На backup для File/SQL умножается на 3. У File 85% IOPS направляется на HDD, 15% на SSD; у SQL активный I/O в базовой модели направлен на SSD. Если в реальности SQL лежит на HDD, модель это не оправдывает — выводится предупреждение.
- Сеть: `users × roleMbpsFactor × scenarioFactor`, на backup у File ×4.
- График показывает полный профиль выбранного сценария; вертикальная линия — текущая минута. Это не журнал реального сервера.

GHz разных поколений CPU несопоставимы напрямую. Проценты CPU — отношение условного спроса к условной ёмкости, не показания esxtop. Для vCPU:% в таблице используется знаменатель `vCPU × GHz`, поэтому насыщение отдельной ВМ видно отдельно от общего хоста.

## Диски и запас

Ёмкость SSD/HDD суммируется отдельно **только для оценки проекта**. Это не создание общего datastore. Каждый реальный VMFS нужно разместить на конкретном устройстве/LUN; RAID, горячие резервы, контроллер, кэш, блокировки и multipathing не моделируются. Thin представлен назначенным объёмом и приблизительным занятым объёмом, без эмуляции файловой системы.

Предупреждения возникают при назначенном или прогнозно занятом объёме выше 80% пула. 20% — начальный ориентир, не универсальное требование VMware. Для интенсивной записи и длинных снапшотов нужен больший запас. Модель не знает реальных VMDK и не гарантирует завершение консолидации.

## Память и предложения размеров

Отдельно показываются назначенная RAM и активная RAM. Определяется превышение физической памяти назначенными объёмами и высокий прогноз working set. Предложение CPU: `ceil(max(2, demand / (GHz × 0.65)))`, ограничено физическими ядрами. RAM предлагается с запасом относительно активного набора, затем стартовый размер ограничивается исходным профилем роли. Общая сумма приводится к доступному бюджету, если возможно.

Кнопка **не** меняет оборудование, сеть или размеры дисков. Она предлагает стартовые CPU/RAM, а не гарантирует достаточность. Если потребности пользователя принципиально не помещается, предупреждения сохраняются. Снижение ресурсов нельзя применять по одному короткому пику: наблюдайте полный бизнес-цикл, лицензирование и требования приложения.

## Три сетевых режима

1. **Своя LAN + свой WAN:** отдельный VLAN `100 + index`, отдельная VRF firewall и WAN `200 + index`.
2. **Общая LAN + общий WAN:** VLAN 10, WAN 1.
3. **Общая LAN + свой WAN:** NIC 1 — VLAN 10 без default gateway; NIC 2 — transit VLAN `200 + index` со шлюзом в своей VRF. Никакого моста между NIC.

Это адресный **план примера**, а не сканирование вашей сети. Проверьте конфликты VLAN/подсетей.Management намеренно вынесен из пользовательских LAN. Адрес `10.x.0.1` в плане — внутренний интерфейс firewall, а не адрес ESXi. WAN transit не означает выдачу публичного IP непосредственно рабочей ВМ.

При 3+ NIC: management vmnic0, LAN vmnic1, WAN vmnic2. При 2: management vmnic0, LAN/WAN vmnic1 trunk. При 1: всё через vmnic0 trunk с предупреждением об общей полосе и отсутствии физического разделения. Оставшиеся NIC не настраиваются автоматически в team: их можно использовать для отказоустойчивости по отдельному проекту.

Несколько логических WAN могут идти через один физический порт только при соответствующем VLAN handoff/upstream switch и изоляции VRF. Несколько default gateway в одной подсети не обеспечивают такую изоляцию. ВМ firewall учитывает ресурсы, но её VRF/NAT/ACL надо настроить отдельно. При большом числе интерфейсов выводится предупреждение о лимитах выбранного appliance.

## Чего модель не делает

- Не моделирует NUMA, CPU scheduler, Ready/Co-Stop, HA/DRS, точный memory overhead, ballooning и swapping.
- Не рассчитывает реальные latency/IOPS RAID, смешанный размер блока, read/write ratio и очереди контроллера.
- Не учитывает лицензии SQL/RDS/Windows/1С и требования их редакций.
- Не гарантирует безопасность: изоляция зависит от реального firewall, физических сетей и политик.
- Не делает backup и не проверяет совместимость оборудования.
- Не заменяет проект production-инфраструктуры и приёмочные испытания.

## Что измерять после внедрения

CPU Ready/Co-Stop и потребление по ВМ; active/consumed RAM, ballooning и host swap; datastore latency, IOPS и throughput; ошибки/дропы/полосу uplink; время приложений и реальные пики backup. После измерения скорректируйте входные коэффициенты и проект. Сохраните измерения отдельно от расчёта, чтобы не перепутать их происхождение.
