# Постоянная подпись, секреты и выпуск

## Что хранится где

**Закрытые ключи не помещаются в публичный репозиторий.** Это согласованный безопасный вариант первоначальной просьбы. Android keystore и Windows PKCS#12 хранятся в GitHub Actions Secrets и в вашей зашифрованной офлайн-копии. В Git допустимы только публичные сертификаты и SHA-256 отпечатки в `signing/public/`.

Секреты не доступны JavaScript, Android WebView, логам сборки или скачиваемому приложению. Workflow материализует их только во временных файлах runner для подписи. Секреты не передаются в job из pull request.

## Однократная настройка владельцем репозитория

Понадобятся Node.js 22, OpenSSL 3, JDK 17+ (`keytool` в PATH), GitHub CLI с авторизацией владельца и право **Settings → Secrets and variables → Actions → New repository secret**. Текущее подключение Arena это право не имеет: оно получает HTTP 403 при чтении/записи secrets. Поэтому генератор подготовлен, но реальные ключи ещё не заведены.

На своём доверенном компьютере в корне проекта:

```sh
gh auth status
node scripts/setup-signing.cjs
```

Генератор:

1. Создаёт Android RSA-3072 JKS и Windows self-signed code-signing RSA-3072 PKCS#12.
2. Генерирует отдельные криптостойкие пароли, не выводя их в терминал.
3. Загружает закрытый материал через `gh secret set` со stdin, не через аргументы командной строки.
4. Создаёт публичные `signing/public/*-certificate.pem` и `*-certificate.sha256`.
5. Не перезаписывает существующий каталог `local-secrets/`.

После успешной загрузки проверьте список **имён** секретов в GitHub. Сделайте офлайн-копию `local-secrets/` вместе с паролями в зашифрованный архив/менеджер секретов. Не отправляйте её в чат. После проверки резервной копии удалите рабочую копию закрытых ключей. Публичные файлы закоммитьте в рабочую ветку и включите в релиз.

Если авторизация GitHub в вашей среде не позволяет записывать secrets, выполните `node scripts/setup-signing.cjs --local-only`, затем вручную загрузите значения из `local-secrets/github-secrets.json` в Secrets. Не коммитьте этот JSON. После переноса безопасно удалите рабочую копию.

| Secret | Содержимое |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | Android JKS в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | Пароль хранилища |
| `ANDROID_KEY_ALIAS` | Alias ключа |
| `ANDROID_KEY_PASSWORD` | Пароль ключа |
| `ANDROID_CERT_SHA256` | Публичный SHA-256 DER-сертификата |
| `WINDOWS_CSC_LINK` | Windows PFX в base64 |
| `WINDOWS_CSC_PASSWORD` | Пароль PFX |
| `WINDOWS_CERT_SHA256` | Публичный SHA-256 DER-сертификата |

`GITHUB_TOKEN` выдаётся Actions автоматически; отдельный персональный токен в репозитории не нужен. Только итоговый publish job имеет `contents: write`.

## Почему нельзя просто заменить ключ

Android требует совместимой подписи для установки поверх существующего package ID. Новый ключ без заранее подготовленной signing lineage не позволит обновить приложение: пользователю понадобится отдельная миграция/переустановка. Не запускайте генератор повторно для уже распространяемого приложения. Восстанавливайте исходный ключ из защищённой копии.

Для Windows используется тот же сертификат, закреплены его публичный SHA-256 и имя издателя. Перевыпуск сертификата меняет pin и требует спланированной миграции доверия. Не удаляйте старый сертификат из доверенных до завершения миграции.

## Доверенный сертификат vs лабораторный self-signed

Self-signed сертификат обеспечивает целостность и идентичность при правильном закреплении, **но не создаёт публичного доверия Windows**. Он подходит для контролируемой лаборатории. Для распространения среди клиентов используйте доверенный code-signing сертификат вашего издателя, лучше OV/EV или облачный сервис с поддержкой electron-builder. В этом случае измените `publisherName` и пины согласованно, проверьте всю цепочку до выпуска.

Для лабораторной Windows установки администратор может импортировать **только публичный** `windows-certificate.pem` в доверенные корневые текущего компьютера после сверки SHA-256 с независимым источником. Это расширение доверия, его нельзя делать молча. Пример для явно согласованной лаборатории (PowerShell от администратора):

```powershell
Get-FileHash .\windows-certificate.pem -Algorithm SHA256
# Get-FileHash считает хеш PEM-файла, а pin приложения — хеш DER сертификата.
# Точный DER pin находится в windows-certificate.sha256.
certutil -verify .\windows-certificate.pem
Import-Certificate -FilePath .\windows-certificate.pem -CertStoreLocation Cert:\LocalMachine\Root
```

Не добавляйте сертификат в Trusted Publisher без отдельного решения политики безопасности. Updater требует `Get-AuthenticodeSignature.Status == Valid`, точного SHA-256 DER и ожидаемого publisher. Если цепочка не доверенная, обновление отклоняется; отключать проверку нельзя. Для первой установки Windows может показать предупреждение SmartScreen.

## Выпуск

1. Измените версию в `package.json` и `package-lock.json` (`npm install --package-lock-only`). Статические подписи версии в UI обновляются отдельно при релизной подготовке.
2. Пройдите CI на working branch.
3. Создайте аннотированный тег на проверенном commit: `v1.0.1`, например. Версия должна точно совпадать с package.json.
4. Workflow `Signed Android and Windows release` проверяет секреты и public pins, собирает APK и NSIS, проверяет подписи, создаёт `android-update.json`, `latest.yml`, blockmap и `SHA256SUMS.txt`.
5. Только после обеих сборок один publish job создаёт стабильный GitHub Release. Черновики и prerelease не принимаются автообновлением.

Android versionCode вычисляется монотонно для обычных semver релизов; схема ограничена диапазоном Android int32. Не публикуйте более старую версию как latest. Release assets загружаются целиком, а не выдаются пользователям по мере незавершённой сборки.

## Проверки обновлений

- Android: HTTPS, фиксированный репозиторий и asset URL, разрешённые redirect hosts, package ID, увеличение version, SHA-256 APK, текущий сертификат и certificate pin, подтверждение пользователем и системный Package Installer. Поддержка сложной ротации ключей намеренно не включена.
- Windows: `electron-updater`, SHA-512 из `latest.yml`, Authenticode, точный сертификат и publisher; проверка завершается отказом при ошибке PowerShell. Автозагрузка выключена: пользователь подтверждает загрузку, затем отдельно перезапуск.
- Debug/unsigned artifacts из CI не являются релизом и не принимают участие в автообновлении.

## Если ключ или секрет скомпрометирован

Немедленно прекратите выпуск, отзовите доступы/сертификат по процедуре издателя, сохраните журналы выпусков. Подписанный вредоносный пакет нельзя «исправить» удалением checksum. Для восстановления доверия требуется план ротации, новая подпись и безопасная миграция пользователей; для Android может понадобиться переустановка. Простая замена файла в Releases недостаточна.
